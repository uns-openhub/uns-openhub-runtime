# Podman Quadlet Deployment

## Boundary

UNS DataHub uses two explicit deployment adapters:

- Docker uses the generated `docker-compose*.yml` files.
- Podman on Linux uses Quadlet units generated by `uns quadlet`.

Podman Compose is not part of the production deployment path. The
`uns-datahub-tools` repository owns the templates and renderer. The generated
`uns-datahub-runtime` repository contains both the templates and the compiled
renderer so it remains a standalone distribution.

## Render and Install

Initialize `.env` first:

```sh
./bin/uns init -i --engine podman
```

Render into the runtime checkout for review:

```sh
./bin/uns quadlet render --runtime-dir "$PWD"
```

Install system Quadlets after review:

```sh
sudo ./bin/uns quadlet install \
  --runtime-dir "$PWD" \
  --scope system \
  --mode both
```

The installation step only writes definitions under
`/etc/containers/systemd`. It does not call `systemctl`, stop a Compose
deployment, pull an image, or start a container. It refuses to replace a
changed managed file unless `--force` is passed. Forced replacements retain a
timestamped sibling backup.

Use `--scope user` only for a deliberately rootless deployment. Do not mix
rootful and rootless Podman for the same installation because they use
different container, image, network, and volume stores.

## macOS with Podman Machine

macOS does not provide systemd, so it cannot install Quadlet units directly.
For local Podman development, enter the Linux Podman machine and install the
units in its rootless user scope:

```sh
podman machine ssh
cd /absolute/path/to/uns-datahub-runtime
./bin/uns quadlet install \
  --runtime-dir "$PWD" \
  --scope user \
  --mode both
```

Then execute the `systemctl --user` commands printed by the installer. The
runtime checkout must be visible at the same absolute path inside the machine.
Docker on macOS continues to use Docker Compose.

The units are stored inside the Podman machine. Removing or recreating that
machine removes the installed units, but does not alter the runtime checkout
on the macOS host.

## Generated Units

The renderer creates:

- one `uns-datahub.network` unit;
- volume units for PostgreSQL, QuestDB, crypto data, controller runtime
  override, and RTT nodes;
- container units for PostgreSQL, Mosquitto, Caddy, QuestDB, and the
  controller.

Container units use concrete, fully qualified image coordinates and absolute
bind paths. Sensitive values are not copied into the units: PostgreSQL and the
controller receive the selected runtime `.env`, while controller secret files
remain mounted from `.secrets`.

PostgreSQL, Mosquitto, and controller systemd readiness is tied to their
container healthchecks. The controller and Caddy have ordering constraints on
PostgreSQL and Mosquitto, but those constraints do not pull local
infrastructure into a controller-only deployment.

## Existing Volume Migration

Compose commonly prefixes logical volume names with its project name. Quadlet
must therefore not guess that `pgdata` means the volume holding production
data.

Before the first Quadlet start:

```sh
podman volume ls
podman volume inspect <candidate-volume>
```

Set the verified existing resource names in `.env`:

```env
UNS_NETWORK=uns-datahub
UNS_PGDATA_VOLUME=pgdata
UNS_QUESTDB_VOLUME=questdb_data
UNS_CRYPTO_VOLUME=uns_crypto
UNS_CONTROLLER_CODE_VOLUME=controller_code
UNS_RTT_NODES_VOLUME=rtt_nodes
```

For a Compose-managed deployment these values may instead be names such as
`uns_pgdata` or `uns-datahub-runtime_pgdata`. Validate each mapping from live
Podman state. Never infer the production database volume from its suffix
alone.

## Cutover

1. Render and review the units.
2. Record running containers, image IDs, ports, network, and volume mappings.
3. Install the units without starting them.
4. Pull the intended versioned images explicitly.
5. Disable the legacy `uns-controller-podman.service` if it was installed.
6. Stop the old Compose deployment without deleting volumes.
7. Run `systemctl daemon-reload`.
8. Enable and start only the service set printed by `uns quadlet install`.
9. Check `systemctl status`, `journalctl`, Podman health, and application
   endpoints.

Do not run Compose and Quadlet copies simultaneously on the same host ports.

## Rollback

1. Stop the Quadlet-managed container services.
2. Restore the previous managed files from their timestamped backups if the
   definitions changed.
3. Run `systemctl daemon-reload`.
4. Restart the previous Compose deployment with its recorded image tag.
5. Verify that the same network and data volumes are attached before accepting
   traffic.

Stopping or replacing the Quadlet containers does not delete their named
volumes. Operators must still avoid destructive `podman volume rm` or Compose
`down -v` commands during migration and rollback.
